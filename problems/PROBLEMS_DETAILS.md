# PROBLEMS DETAILS

## 1. Logout link never signed out

**Found:** 2026-08-15, e2e verification pass after v1 landed (POST /logout check 400, post-logout / still 200).
**Root cause:** parallel beads — tailwind bead (4ei.2) wrote nav with plain `<a href="/logout">` before auth existed; auth bead (4ei.4) was scoped away from _Layout.cshtml and only added a GET /logout dead-link guard that redirects to `/` without signing out. Net: UI logout did nothing.
**Fix (med-history-4ei.11):** `_Layout.cshtml` anchor → inline `<form method="post" action="/logout">` with `@Html.AntiForgeryToken()` + styled submit button; rendered only when authenticated.
**Regression coverage:** e2e verify script (scratchpad) asserts POST /logout → 302 and next `/` → 302 login. No unit test — defect was markup-only, no extractable decision logic.

## 2. AddDataProtectionKeys migration recreated Logs table

**Found:** 2026-08-15, nvs.3 builder's container smoke test (`relation "Logs" already exists`, then DataProtection keyring 500s on every request).
**Root cause:** nvs.2 (DataProtection) and 4ei.14 (logger) both changed the EF model in parallel worktrees. During the nvs.2 rebase-landing, `dotnet ef migrations remove` + `add` was run against a snapshot that had been reverted to a state missing LogEntry — the regenerated migration diffed model-with-Logs against snapshot-without-Logs and emitted a duplicate `CreateTable("Logs")`, never creating DataProtectionKeys. Orchestrator's verification grep miscounted and let it land.
**Fix (med-history-nvs.8):** restored snapshot from post-AddLogsTable commit (1a0d310), deleted broken migration, regenerated — new Up() creates only DataProtectionKeys. Verified on throwaway Postgres: full clean chain AND partial-failure recovery (DB stuck after AddLogsTable applies the fixed migration cleanly).
**Regression coverage:** e2e — migration chain applied + login round-trip (exercises keyring write) on fresh containerized Postgres. No unit test: defect lives in generated migration code, no extractable pure logic. Process guard added to memory: when parallel beads both touch the EF model, regenerate the later migration from the merged snapshot and diff-review the migration body before landing.

## 3. Deployed app rendered all dates/times in UTC

**Found:** 2026-08-15, user noticed dates off by 7 h on the Cloud Run deployment (local dev looked fine).
**Root cause:** `AppTime` is built on `TimeZoneInfo.Local` / `DateTime.Now` ("v1 treats server-local time as the user's time zone" — `AppTime.cs` comment). Dev machine is Asia/Bangkok so everything looked right locally; Cloud Run containers run UTC, so `TimeZoneInfo.Local` = UTC in prod and every day grouping, time label, and form default rendered in UTC. Same pattern also live in `HistoryController.cs:27` and `EntriesController.cs:33`.
**Fix (med-history-5eu):** `ENV TZ=Asia/Bangkok` in the Dockerfile final stage. Debian `aspnet:10.0` base ships tzdata, so the env var alone flips `TimeZoneInfo.Local`. Code-level pinning (`FindSystemTimeZoneById("Asia/Bangkok")` inside `AppTime`) was considered and deliberately deferred — chosen fix keeps v1's server-local design and moves the knob to the image.
**Regression coverage:** none feasible — fix is a container env var, no app code changed; `TimeZoneInfo.Local`-dependent logic can't assert a zone the test host doesn't have. Guard is the Dockerfile comment: if the base image ever moves to chiseled/alpine (no tzdata), TZ silently stops working — revisit code-level pinning then.

## 4. Lightbox dialog stuck top-left on mobile

**Found:** 2026-08-15, user viewing photo lightbox (med-history-h3f) on iPhone 15 Pro Max — image not centered.
**Root cause:** Tailwind v4 preflight emits `@layer base { *, :after, :before, ::backdrop { margin: 0; ... } }`. Native `<dialog>` centering comes from the UA stylesheet's `margin: auto` (with `position: fixed; inset: 0`); the preflight universal reset overrides it, so the modal renders at the viewport's top-left. Desktop masked it — image large enough to near-fill the viewport.
**Fix (med-history-3c4):** `m-auto` added to the `<dialog>` class list in `_Lightbox.cshtml`, restoring auto-margin centering on both axes.
**Regression coverage:** none — markup-only, one utility class, no extractable decision logic (same call as problem 1). Gotcha worth remembering: any future native `<dialog>` needs `m-auto` under Tailwind preflight.

## 5. Fast double-tap on a login keypad digit zoomed the page

**Found:** 2026-08-16, iOS user report — tapping the same digit twice quickly on `/login`'s passcode keypad zoomed the page instead of registering two taps.
**Root cause:** Safari's double-tap-to-zoom gesture triggers on a fast repeat tap of the same element; the keypad buttons had no `touch-action` set, so the default `auto` left the gesture live on top of the `click` handler the passcode JS listens for.
**Fix (med-history-p30):** `touch-action: manipulation` (Tailwind `touch-manipulation`) added to the `#passcode-keypad` grid AND to every digit/backspace button — the container alone is not reliable across Safari versions since the button, not its ancestor, is the actual tap target. Viewport meta tag left untouched (no `user-scalable=no` / `maximum-scale`) so page-wide pinch-zoom still works; this is a targeted fix on the keypad's own tap targets, not a page-wide zoom kill. While in that markup, also added `active:bg-black active:text-white dark:active:bg-neutral-100 dark:active:text-neutral-950` alongside the existing `hover:` pair — touch has no real hover, so the `hover:` inversion was sticking after a tap until the reader tapped elsewhere ("stuck pressed"); `active:` gives immediate tap feedback instead and matches the existing light/dark hover pairing.
**Regression coverage:** none — defect is a CSS touch-gesture behaviour in a view (`Login.cshtml`), not decision logic; there is nothing here to extract into a pure function to unit test.

## 6. Clearing the photo picker let a stale in-flight result win

**Found:** 2026-08-18, orchestrator's diff review of med-history-4ei.26 — found in review, never observed in the field.
**Root cause:** the photo `change` handler in `Views/Entries/Form.cshtml` guards against re-selection races with a `photosGeneration` counter: each run captures `var generation = ++photosGeneration` and every async continuation bails when `generation !== photosGeneration`. The bump sat *after* the `if (files.length === 0) return;` early return, so clearing the picker was the one path that did not invalidate work already in flight. A selection whose async work was still pending therefore still matched the counter and its continuations ran against a picker the user had just emptied. Two halves were affected: the pre-existing downscale swap re-populated `photosInput.files` with the previous selection's processed files after the user cleared them (so a cleared form silently uploaded the old photos), and the EXIF read added by this bead re-revealed the "Use photo date" button — clicking it would stamp the entry with the capture time of a photo that was no longer being uploaded, i.e. wrong data in a medical log. The downscale half is a latent defect that predates this bead; the EXIF half inherited it by reusing the same counter.
**Fix (med-history-4ei.26):** move `var generation = ++photosGeneration;` above the early return, so the empty-selection path invalidates everything in flight. One move repairs both halves; the rest of the counter semantics are unchanged.
**Regression coverage:** no automated test — this is browser JS and the project has no JS test runner, which the user explicitly chose not to add for this bead (no npm dependency, parser and wiring stay inline in `Form.cshtml`). Verified instead with a DOM-stub harness kept in the session scratchpad, not the repo: it loads the real `<script>` body straight out of `Form.cshtml` and drives it against stubbed `document` / `File` / `DataTransfer` / `createImageBitmap`. The case that covers this bug fires `change` for a selection with EXIF, fires `change` again with an empty file list before the first read settles, then asserts the button stays hidden *and* `photosInput.files` is still empty. It fails on the old ordering and passes on the fix. Keep that harness shape in mind for any future change to this handler — the bug class is "async continuation outlives the selection that started it", and the counter is the only thing standing between it and a wrong timestamp.

## 7. Editing an entry from search or the type report dumped the reader on the day page

**Found:** 2026-08-21, filed as med-history-4ei.27 — editing an entry from the search results and saving landed on the entry's day page, with the query and page number gone.
**Root cause:** the entry form has three entry points — `Views/Day/_Entries.cshtml`, `Views/Search/Index.cshtml`, `Views/TypeReport/Index.cshtml` — and one exit. `EntriesController.RedirectToDay` was hard-wired to `Day/ByDate` and was the return of Create, Update *and* Delete; Cancel in `Views/Entries/Form.cshtml` was a hard-coded `/day/{cancelDay}` href. Nothing ever recorded which list the form was opened from, so every exit guessed the same one. From the day page the guess is right by accident, which is why it stood: the two list pages that carry state in their query string — search (`q` + `page`) and the type report (`types` + `page` + `sort`) — were the ones that lost it, and losing it meant re-running the search and paging back after every single edit.
**Fix (med-history-4ei.27):** returnUrl round-trip. Each of the three lists appends its own address to its edit links (`RedirectRules.WithReturnUrl`, escaping the origin whole so the report's repeated `types` parameters do not leak into the link's own query); `GET /entries/{id}/edit` takes `returnUrl` onto `EntryFormViewModel`; the form renders it as a hidden input in all three of its forms — save, delete entry, remove photo — so it survives a validation re-render and a mid-edit photo removal (`PhotosController.Delete` hands it back to the edit page); `POST /entries/{id}` and `POST /entries/{id}/delete` redirect to it. `Create` deliberately keeps redirecting to the new entry's day. The day page's edit links build their origin from `DayViewModel.Day`, **not** from the request — that partial is also the tick fragment's payload, and reading the request there would name the checklist's POST route as the origin.
**Open-redirect note:** returnUrl arrives as posted input, so every use of it goes through `RedirectRules.Sanitize`, which is `Url.IsLocalUrl` — the framework's own check, injected as a predicate rather than reimplemented. An off-site value (`https://evil.example`, `//evil.example`) is dropped at the door: not followed, and not echoed back into the page's hidden inputs or Cancel href either.
**Behaviour change worth knowing:** an edit that moves an entry to another date now returns to the origin rather than following the entry to its new day — including from the day page, whose origin is the day the edit started on. That is the bead's frozen contract: the reader asked to go back to a list, and the entry's new date shows up in that list.
**Regression coverage:** `MedHistory.Tests/RedirectRulesTests.cs`, 27 cases over the three pure functions — local path kept, null/empty/whitespace and off-site (absolute http(s), protocol-relative `//`, backslash `/\`, `javascript:`) all falling back, escaping of an origin whose own query contains `&` and `=`, and a round-trip case that pushes an origin through `WithReturnUrl` and back out of `Resolve`. The predicate under test is the real `Url.IsLocalUrl` off a bare `UrlHelper`, not a hand-rolled imitation — imitating it would have tested the imitation, and locality is the security-relevant half.

## 8. Login dropped back to the passcode screen after closing the browser

**Found:** 2026-08-22, user report — on mobile Safari especially, closing the browser and reopening the app forced the 6-digit passcode again, well inside the 30-day window the cookie is configured for.
**Root cause:** `AccountController.Login`'s `HttpContext.SignInAsync(scheme, principal)` call passed no `AuthenticationProperties`, so `IsPersistent` defaulted to `false` and the browser received a session cookie regardless of the cookie handler's `ExpireTimeSpan = 30 days` + `SlidingExpiration = true` in `Program.cs`. A session cookie is discarded by the browser itself on close — mobile Safari does this aggressively — so the 30-day sliding ticket never got a chance to apply.
**Fix (med-history-4ei.29):** new pure `AuthCookieRules.SignInProperties()` returning `new AuthenticationProperties { IsPersistent = true }`; `AccountController.Login` passes it as the third argument to `SignInAsync`. Cookie lifetime itself (`ExpireTimeSpan`, `SlidingExpiration`, `HttpOnly`) is unchanged in `Program.cs` — this only stops the browser from treating the cookie as session-scoped.
**Regression coverage:** `MedHistory.Tests/AuthCookieRulesTests.cs` asserts `SignInProperties().IsPersistent == true` — fails on the old no-properties call site (which had no equivalent to assert against; the test pins the fixed behaviour going forward) and passes on the fix.

## 9. English survived in the places no slice owned

**Found:** 2026-08-22, during the typography pass of the i18n epic (med-history-4ei.31.8) — Thai was on every screen, and three runs of English were still on the page with it.
**Root cause:** two distinct failures that happened to land in the same review.

The first is ownership. The epic was cut into slices by screen — chrome, day page, meds, reports — and `Views/Shared/_ConfirmDialog.cshtml` and `Views/Shared/_Lightbox.cshtml` belong to no screen. The layout renders them once for the whole app, so every slice read past them: the chrome slice owned `_Layout` and `Error`, the day slice owned `Views/Day`, and the two partials sat in the gap. The confirm dialog is the one that mattered — it is on every destructive action in the app, so the most consequential button in the product asked for confirmation in English on a Thai page.

The second is shape, and it would have survived any slicing. `ChecklistRules.ProgressLabel` returned `$"{done} of {rows.Count} meds done"` — by the time a view has that string, the sentence has collapsed and there is no key left to look up. The same defect in a second form: `MedPlanRules.DescribeAllocation` joins meal and method words into `"after meal · eyedrop"`, and both views showing one rendered the joined result raw.

**Fix (med-history-4ei.31.11):** `Resources/Views/Shared/_ConfirmDialog.th.resx` and `_Lightbox.th.resx`; the dialog's Cancel comes from `SharedResource` rather than a second copy, since it is the same word half the app's forms use. `ChecklistRules.Progress` and `MedStockRules.RemainingLabel` now return a `RuleMessage` — the key plus its numbered args — and the view formats them into the *translated* string, so Thai puts the counts where Thai puts them. `RemainingLabel` returns `RuleMessage?` and hands back **null** when nothing stocks the medication: an empty key would have rendered "(0 left)" and claimed it had run out. The two views showing a description split it back apart and look each part up on its own.

**The near-miss inside the fix:** the first cut of that split declared its own `const string partSeparator = " · "` in the view, and `Views/Meds/Index.cshtml` already had one of its own. `MedPlanRules.PartSeparator` was `private`, so nothing tied the copies to the constant they had to match — change the separator and the split silently stops matching, the description renders as one unlooked-up English blob, and no test fails. The constant is now public and both views split on it, which is the only reason it is public.

**Regression coverage:** four tests, each verified failing first.
- `ViewLiteralUsageTests` walks every `.cshtml` for the *shape* of the miss rather than a list of known strings — a run of English with no `@` in it went through no lookup, by definition — in body text and in the five attributes a reader is read out of. A second fact feeds it a synthetic view containing exactly the three original misses beside seven things it must stay quiet about, so it cannot pass by having stopped looking.
- `ResourceLayoutTests.EveryLineTheChecklistSummaryCanReadIsAKeyInTheChecklistsOwnFile` drives all three branches of `Progress` and looks up whatever key comes back; `TheStockCountAChecklistRowPrintsIsAKeyInTheChecklistsOwnFile` does the same for the stock count.
- `EveryDescriptionTheRulesComposeSplitsBackIntoKeysTheViewLooksUp` walks every `MealRelation` × `MedMethod` pair through the real `DescribeAllocation`, splits it the way the views do, and asserts each part resolves to non-empty Thai in the file that view reads. Changing `Join` to a different separator fails it.
- `AViewThatSplitsADescriptionUsesTheRulesOwnSeparatorAndNotACopyOfIt` covers the half the round trip structurally cannot see: it splits on the constant itself, so it stays green no matter what a view does. This one reads the two views' source and asserts they name `MedPlanRules.PartSeparator` and hold no `" · "` literal. It is scoped to those two paths **by name**, not swept across every view containing a middot — `DoctorReport/Index.cshtml` joins its own list of type counts on one, is coupled to nothing, and routing it through `PartSeparator` would tie two unrelated strings together and let a separator change silently edit the printed doctor report.

**The lesson worth keeping:** slicing a translation by screen leaves the shared partials to nobody, and a missing translation is the quietest defect there is — nothing throws, the page renders, and it reads correctly to everyone who tests it in English.
