# Languages: English and Thai

Two cultures, `en-US` (default) and `th-TH`. Plan and slice list: [`plans/epic-i18n-th.md`](../../plans/epic-i18n-th.md).
Why Buddhist-era dates come free and how they leak: [`docs/spike-i18n-th.md`](../spike-i18n-th.md).

## How the language is chosen

`UseRequestLocalization` runs **before routing**, so `CurrentCulture` / `CurrentUICulture` are the
reader's choice by the time anything renders — views, validation messages, error pages.

Its provider list is **cleared down to `CookieRequestCultureProvider` alone**. `Accept-Language` is
deliberately not consulted: a Thai-configured browser would otherwise render the doctor report in a
language the person printing it never asked for. The language changes when the toggle says so, and
never otherwise.

## The toggle

`POST /culture` (`CultureController`) is the only writer of the culture cookie
(`.AspNetCore.Culture`, essential, one year). It is `[AllowAnonymous]` — the login screen needs it,
since a reader who cannot read the passcode prompt cannot log in to change the language.

It is a **plain form post**, not JavaScript: the server renders the chosen language on first paint
instead of correcting it afterwards, and it works with scripting off. `returnUrl` is posted input
like any other and goes through `RedirectRules.Resolve`, so an off-site value is dropped rather
than followed.

The toggle renders in three places — desktop nav, mobile panel, and a minimal right-aligned bar for
the logged-out pages — so, like the theme toggle, **nothing about it may key off an id**. The button
shows the language a click moves to (`TH` while reading English); `aria-label` spells out the
sentence, since two letters tell a screen reader nothing.

All the branching lives in pure `CultureRules`: supported list, case-insensitive `IsSupported`,
`Toggle`, `ShortLabel`, `LanguageName`. An unknown or missing current culture toggles to `th-TH`,
not to the default — a broken cookie already renders the default, so offering to switch to it would
be a button that visibly does nothing.

## Where the strings live

> **Invariant:** a resource key **is** the English source text — `@L["Save"]`, not `@L["SaveButton"]`.
> A lookup that finds nothing returns the key, so **English needs no `.resx` at all**. Only
> `*.th.resx` files are ever written, and an untranslated key silently reads as English instead of
> blowing up. `AddLocalization(o => o.ResourcesPath = "Resources")` in `Program.cs` is what points
> the lookup at `MedHistory/Resources/`.

Two files answer "where does this string go":

| Copy | File | Base name the framework computes |
|---|---|---|
| Used in more than one area | `Resources/SharedResource.th.resx` | `MedHistory.Resources.SharedResource` |
| Used by one view | `Resources/Views/<Controller>/<View>.th.resx` | `MedHistory.Resources.Views.<Controller>.<View>` |

The per-view path **mirrors the view's own path** — `Views/Shared/_Layout.cshtml` →
`Resources/Views/Shared/_Layout.th.resx` — because that is literally how `IViewLocalizer` derives
the name. A layout and a partial each get their own file; nothing is inherited down.

`SharedResource` is the empty marker class at `MedHistory/SharedResource.cs`, the standard
`IStringLocalizer<T>` anchor. It must stay in the **root namespace and at the project root**: the
factory strips the root namespace off the type's full name and prefixes `Resources.`, so a move
would repoint every shared string at a file that does not exist.

> **Invariant:** a misplaced `.resx` still compiles, still ships, and every lookup silently falls
> back to English. Nothing in the build notices — `ResourceLayoutTests` is what does, by doing the
> same `ResourceManager` lookup through the same base names.

The shared file holds the cross-area vocabulary only: Save, Cancel, Delete, Remove, Edit, Add,
Back, Today, History, Reports, Search, Types, Logout, and the five report names. Parallel slices all
write to that one file, so additions there stay **append-only**.

### Using them from a view

`Views/_ViewImports.cshtml` injects both, once, for every view:

- `Localizer` (`IViewLocalizer`) — this view's own file.
- `L` (`IHtmlLocalizer<SharedResource>`) — the shared vocabulary.

Indexer for body text (`@L["Today"]`), **`GetString(...)` in attributes and script**
(`aria-label="@Localizer.GetString("Menu")"`): the indexer returns an `IHtmlContent`, which would
slip past the encoding an attribute needs, and `LocalizedHtmlString.Value` is the *unformatted*
resource — `GetString(key, args)` is the one that applies `string.Format`.

### Copy that a script assembles

The theme toggle builds its `aria-label` in the browser, because only the script knows which mode
is live. Thai must not be hardcoded there. The layout serializes `{ sentence, names }` to JSON —
which also escapes it safely into the `<script>` — keyed by the same three mode strings the
script's `next` map cycles through, so the cycle keeps exactly one definition and the `medTheme`
contract and the `.theme-toggle` class binding are untouched. The passcode screen's live region
(`{0} of {1} digits entered`) travels the same way, and the server's first paint formats the same
template so the two cannot drift.

`CultureRules.LanguageName` returns a **resource key**, not copy — the layout looks it up. That is
what lets `CultureRules` stay pure while the toggle's `aria-label` still reads "เปลี่ยนเป็นภาษาอังกฤษ".

## Dates and identifiers

`th-TH` resolves to `ThaiBuddhistCalendar`, so Thai dates read `ส. 22 ส.ค. 2569`. Digits and
separators are unchanged from English.

> **Invariant:** identifier-shaped strings are formatted with an explicit `CultureInfo.InvariantCulture`
> — day keys in `/day/<key>`, `<input type="month">` and `<input type="datetime-local">` values,
> posted decimals. Display formatting is a separate, deliberate path.

The split, in code:

| | Identity — invariant, no culture parameter | Display — takes a `CultureInfo` |
|---|---|---|
| day | `AppTime.Key`, `AppTime.TryParseDay` | `AppTime.DayLabel` |
| time | `AppTime.InputValue`, `AppTime.TimeInputValue` | `AppTime.TimeLabel` |
| month | `ReportRules.MonthKey`, `ReportRules.TryParseMonth` | `ReportRules.MonthLabel`, `ReportRules.WeekdayLabels`, and `Label(culture)` on the three month records |

Display helpers take the culture as an **argument** rather than reading the ambient one, so a test
pins it instead of inheriting the machine's; every call site passes `CultureInfo.CurrentUICulture`,
which request localization has already set. `AppTime.TimeInputValue` exists only to keep a
`<input type="time">` default off the display path — it reads identically to `TimeLabel` in both
languages, which is exactly why sharing one helper would have gone unnoticed.

The leak is quiet, not loud: a Buddhist-era `2569-08-22` **parses back cleanly** as the year 2569,
so nothing throws — the page just links five centuries out. `CultureFormattingUsageTests` therefore
walks every `.cs` and `.cshtml` in `MedHistory/` and fails on a date/time format string handed to
`ToString`, `string.Format` or an interpolation without a `CultureInfo`, listing file and line.

## Thai typography — the `th:` variant

Thai stacks a vowel and a tone mark **above** the base consonant (`เช้า`, `น้ำหนัก`, `ตึงเครียด`) and
sara u **below** it, so a line of Thai carries ink past where Latin at the same size stops. Two
shapes of control put a border in the way of it, and neither fails loudly — the marks are shaved or
graze the border, which reads as a font artifact rather than as a bug:

| Shape | Why it collides | What fixes it |
|---|---|---|
| `leading-none` on a chip that holds a word | the line box is pinned to 1em, under the ink | `th:leading-normal` |
| an **inline** bordered chip with no `py-*` | an inline box's border is drawn on the font's ascent, not on the line box — **line-height cannot reach it** | `th:py-0.5` |

`@custom-variant th (&:lang(th))` in `Styles/site.css` is the whole mechanism. `<html lang>` already
carries the active culture, and `lang` inherits, so `:lang(th)` matches every element on a Thai page
and nothing on an English one. The trailing `:lang(th)` also outweighs the bare utility on
specificity, so `leading-none th:leading-normal` overrides regardless of emission order.

> **Invariant:** a control that pins its height to the font size — `leading-none`, or an inline
> border with no vertical padding — carries its `th:` counterpart **on the same line**, exactly the
> habit `dark:` already has. English is never touched: the fix raises line-height for Thai rather
> than shrinking type for both.

`ThaiTypographyUsageTests` guards the quiet half. Tailwind does not error on an unknown variant, it
just emits nothing — so deleting or renaming `@custom-variant th` would revert every Thai control to
the Latin metric with a green build. The test asserts views and stylesheet still agree on the name.

`leading-none` is **kept** where the control holds no localized word: the three month grids
(`Report`, `AnxietyReport`, `WeightReport`) are day numbers, `2/3` progress and an emoji, and the
lightbox close button is `×`.

### Wrapping

Thai is written without spaces between words, so a run has none of the break opportunities English
gets for free; browsers segment it with a dictionary instead. Where that finds no break — a
transliterated drug name, an unusual compound — the run overflows its column, and on the printed
doctor report an overflowing line is simply lost rather than scrollable. The free-text columns
therefore carry `wrap-break-word` as a backstop, and `History`'s type chips carry `wrap-anywhere`
because that column has no `min-w-0` to shrink through and only `anywhere` is counted when the flex
algorithm asks how narrow a column can get. Both are inert for English, where a word always fits.

> **Caveat:** `:lang(th)` keys off the **UI** language, not the language of the user's own text. Type
> and medication names typed in Thai while reading the English UI get the wrapping backstop (it is
> unconditional) but not the chip padding. Making the padding unconditional is a two-pixel change to
> the English chip, which is why it was not taken.
