# Languages: English and Thai

Two cultures, `en-US` (default) and `th-TH`. Plan and slice list: [`plans/epic-i18n-th.md`](../../plans/epic-i18n-th.md).
Why Buddhist-era dates come free and how they leak: [`docs/spike-i18n-th.md`](../spike-i18n-th.md).

## How the language is chosen

`UseRequestLocalization` runs **before routing**, so `CurrentCulture` / `CurrentUICulture` are the
reader's choice by the time anything renders — views, validation messages, error pages.

Its provider list is **cleared down to `CookieRequestCultureProvider` alone**. `Accept-Language` is
deliberately not consulted: a Thai-configured browser would otherwise render the doctor report in a
language the person printing it never asked for. The language changes when the toggle says so, and
never otherwise.

## The toggle

`POST /culture` (`CultureController`) is the only writer of the culture cookie
(`.AspNetCore.Culture`, essential, one year). It is `[AllowAnonymous]` — the login screen needs it,
since a reader who cannot read the passcode prompt cannot log in to change the language.

It is a **plain form post**, not JavaScript: the server renders the chosen language on first paint
instead of correcting it afterwards, and it works with scripting off. `returnUrl` is posted input
like any other and goes through `RedirectRules.Resolve`, so an off-site value is dropped rather
than followed.

The toggle renders in three places — desktop nav, mobile panel, and a minimal right-aligned bar for
the logged-out pages — so, like the theme toggle, **nothing about it may key off an id**. The button
shows the language a click moves to (`TH` while reading English); `aria-label` spells out the
sentence, since two letters tell a screen reader nothing.

All the branching lives in pure `CultureRules`: supported list, case-insensitive `IsSupported`,
`Toggle`, `ShortLabel`, `LanguageName`. An unknown or missing current culture toggles to `th-TH`,
not to the default — a broken cookie already renders the default, so offering to switch to it would
be a button that visibly does nothing.

## Dates and identifiers

`th-TH` resolves to `ThaiBuddhistCalendar`, so Thai dates read `ส. 22 ส.ค. 2569`. Digits and
separators are unchanged from English.

> **Invariant:** identifier-shaped strings are formatted with an explicit `CultureInfo.InvariantCulture`
> — day keys in `/day/<key>`, `<input type="month">` and `<input type="datetime-local">` values,
> posted decimals. Display formatting is a separate, deliberate path.

The split, in code:

| | Identity — invariant, no culture parameter | Display — takes a `CultureInfo` |
|---|---|---|
| day | `AppTime.Key`, `AppTime.TryParseDay` | `AppTime.DayLabel` |
| time | `AppTime.InputValue`, `AppTime.TimeInputValue` | `AppTime.TimeLabel` |
| month | `ReportRules.MonthKey`, `ReportRules.TryParseMonth` | `ReportRules.MonthLabel`, `ReportRules.WeekdayLabels`, and `Label(culture)` on the three month records |

Display helpers take the culture as an **argument** rather than reading the ambient one, so a test
pins it instead of inheriting the machine's; every call site passes `CultureInfo.CurrentUICulture`,
which request localization has already set. `AppTime.TimeInputValue` exists only to keep a
`<input type="time">` default off the display path — it reads identically to `TimeLabel` in both
languages, which is exactly why sharing one helper would have gone unnoticed.

The leak is quiet, not loud: a Buddhist-era `2569-08-22` **parses back cleanly** as the year 2569,
so nothing throws — the page just links five centuries out. `CultureFormattingUsageTests` therefore
walks every `.cs` and `.cshtml` in `MedHistory/` and fails on a date/time format string handed to
`ToString`, `string.Format` or an interpolation without a `CultureInfo`, listing file and line.
